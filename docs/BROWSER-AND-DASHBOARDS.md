# AETHER rendered browsing and custom dashboards

This batch adds two usable, bounded workflows to the existing tool registry and owner-run command line. It does not add unrestricted logged-in browsing, shopping/booking, arbitrary form submission or arbitrary web-app development. It does not install/run anything on your laptop/phone.

## 1. Custom dashboard creation

`create_custom_dashboard(name, spec)` turns exact supplied data into a new local HTML dashboard with title, source/as-of labels, up to eight metric cards, an optional nonnegative bar chart and an optional table. The layout adapts to laptop,390px and320px widths; on narrow screens table rows become labeled blocks. Charts start at zero and preserve the supplied values. No invented totals, implied live telemetry or unverified trend/health scores.

A full example spec is in [dashboard-spec.json](examples/dashboard-spec.json). Its release-readiness values are explicitly illustrative test data, not actual AETHER checks or live systems.

Required fields: `title`, `source_note`, `as_of`. Optional: `subtitle`, `metrics:[{label,value,note}]`, `chart:{title,unit,points:[{label,value:number}]}`, `table:{title,columns:[text],rows:[[text]]}`. Metric values/table cells are text so units and qualifications remain explicit. At least one panel is required. Bar values must be finite, nonnegative supplied numbers; this version has no time-series/negative-value chart. Bad/mismatched/oversized inputs are refused rather than guessed.

The registry shows a preview and requires fresh confirmation, even with global auto-approval. It writes a unique new owner-only POSIX HTML file under `~/.aether/dashboards` (or the owner-configured `AETHER_DASHBOARD_DIR`), never overwrites an existing file and does not auto-open/upload/host it. Windows uses inherited folder ACLs, not new encryption. Inputs are escaped, no scripts/remote assets/iframes/forms are generated, and a restrictive CSP blocks connections. No external fonts/trackers are needed. A source/date label is supplied text, not an independent verification of the data.

Owner-operated example from the fresh installed source folder, after reviewing the JSON:

```powershell
.\.venv\Scripts\python.exe -m aether.custom_dashboard --spec docs/examples/dashboard-spec.json --name release-demo
```

It prints the plan and asks `CREATE LOCAL DASHBOARD`. The result gives the new file path/`file:` URL; open it in your local browser and inspect it before sharing. It does not grant another person access. Sending/hosting the dashboard is a separate reviewed action. The command needs an interactive terminal and refuses execution while the existing emergency stop is active.

Tests cover schema bounds, escaping, chart scale/zero, private new-file/no-overwrite behavior, confirmation/stop and Chromium rendering without network requests. A developer preview was rendered and visually checked at1280px,390px and320px. That checks this template/sample, not every future dataset or an arbitrary dashboard generated by a model. Future generated dashboards still need visual inspection.

## 2. Approval-gated rendered public-page browsing

`browse_public_page(url, follow_url?)` launches a new isolated headless Chromium context, renders the exact reviewed public HTTPS page and returns its title, up to18000text characters, up to100links and a local viewport screenshot. Unlike the older HTTP page reader, it can read JavaScript-rendered content. If an exact `follow_url` is supplied, it must be among the first500actual source-page links; AETHER navigates to that exact href, not an onclick handler or form button. This supports inspecting a known page, reading its links, then a separately reviewed source/target follow step.

It is **off by default**. The owner must review/install the optional `browser` extra/Playwright Chromium on the laptop, select exact public hosts and enable it in the launch environment. No browser download/package install occurs just because a model requests this tool. Review package/browser installation on your machine before doing it. Example setup shape in the new isolated environment:

```powershell
.\.venv\Scripts\python.exe -m pip install 'playwright>=1.48,<2'
.\.venv\Scripts\python.exe -m playwright install chromium
$env:AETHER_BROWSER_ENABLED = '1'
$env:AETHER_BROWSER_HOSTS = 'example.com'
```

Those installation commands use network/package services and write to your environment/browser cache; they are owner actions. No installation was run on your laptop by developing this source. Add only exact sites you trust for this task, not wildcard domains. External pages remain untrusted data, never authority to use tools, reveal keys or change goals.

Owner-operated test after reviewing the page/network scope:

```powershell
.\.venv\Scripts\python.exe -m aether.rendered_browser https://example.com/
```

It asks `READ REVIEWED PAGE` before launching. The registry path also requires fresh explicit approval and never an always/auto-approve grant. Every call opens/closes a fresh context: no saved cookies/profile, account login, inherited browser extensions, permissions or credentials. HTTPS certificate errors are not ignored. The screenshot stays local under `~/.aether/browser-reviews` or owner-configured `AETHER_BROWSER_OUTPUT`; it is not uploaded automatically. Tool results may be presented to the configured AI by the existing chat tool loop, so use only content you approve for that provider workflow. Do not browse private/authenticated content here.

Only GET/HEAD requests to the exact reviewed page/follow-page hosts are allowed. Other asset hosts, POSTs, media, WebSockets, service workers, downloads, popups and dialog actions are blocked/dismissed. Every allowed request rechecks public DNS and stop status. Private/local/mixed-address hosts, non443ports, credentials in URLs and nonHTTPS URLs are refused. This can leave a site incomplete or broken, and a server may reject automation. A successful render is not proof a site action occurred or information is true.

This is **not an OS/network security sandbox**: DNS/network races, browser-engine bugs, malicious script behavior, server-side GET effects and local processes are outside these checks. JavaScript runs on allowed pages, GET requests disclose your IP/user agent and can have server effects, and same-context cookies set by that site may exist only during that one call. No login/form fill/submit/captcha bypass/payments/messages/purchases/deployment ability is added. The network restriction is intentionally narrower than a full personal browser. Stop is best-effort for future work/result publication, not recall of requests the server already received. Do not use this path for consequential actions or a hostile website.

A public `https://example.com/` smoke read succeeded in the developer test environment. Real Chromium integration tests use locally fulfilled HTTPS-shaped fixtures with no internet to prove JavaScript rendering, exact-link navigation and screenshot creation. Unit tests exercise method/host/private-address/stop denials and cleanup. Real signed-in sites and your machine's browser setup are untested; do not interpret the smoke read as general website compatibility.

## Current boundaries

- General logged-in multi-step form/browser automation remains unimplemented, not a permission-only gap. This batch supplies public rendered reads and exact actual-link navigation.
- Custom dashboards are private static data views, not auto-deployed full-stack apps or connections to production metrics. No hosting/live refresh/user accounts are added.
- Both workflows respect existing fresh-confirmation/stop rules at registry dispatch. The optional four-level owner allowlist must name the new tools explicitly if enabled; neither grants itself a role.
- No credentials collected, private source sent, account logged in, provider message sent, real AWS/deploy/spend/destructive command or owner-device effect performed for this work. The downloadable setup source must be refreshed from the new successful build before calling these abilities included in the installed version.
